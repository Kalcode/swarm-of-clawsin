# Build a tiny world, then grow the swarm

Yes, install oMLX. On your 32-core-GPU M1 Max it is the best server for a swarm because it does three things at once: it runs many agents' requests through the model in a single pass, it reuses the shared opening of every agent's prompt, and it forces replies into a format your world can parse. The Ollama you already have still makes simultaneous requests wait in line on its fast MLX engine. In a late-October M1 Max test its throughput stayed flat and waits reached 30 seconds ([lilting.ch](https://lilting.ch/en/articles/m1-max-llm-engine-benchmark)). Run one small model shared by every agent: a 9B-class Qwen for smarter agents or a 4B-class model for more of them. By my estimate that supports about 25 agents each thinking every 10 to 20 seconds, and 50 or more if they only think when something happens to them. Build the world AI-first and seen from inside one creature, the way a single dwarf lives in Dwarf Fortress. The world keeps the real state. A perception layer turns what each creature can see, hear, hold and feel into a short first-person text. An action layer turns its stated intentions ("walk to the oak", "chop", "tell Mara I have stone") back into changes in the world. That rules out driving existing games through their human interfaces of pixels, keystrokes and screen scraping. No open-source game pairs Dwarf Fortress depth with that inside view, multiplayer and in-world scripting, so the best path is a small world you write yourself, with a thin agent loop instead of an agent framework. Text is fine, and a visual viewer for you is optional. Other computers in the house join the way players join a multiplayer server: a script starts a local model, connects to your world and runs its own agents. Expect more social behavior, not more intelligence. In one Minecraft study, collaboration success fell from up to 90% to under 30% when going from 2 to 5 agents ([MineCollab](https://arxiv.org/html/2504.17950v1)). The realistic route to a stronger collective is cultural accumulation: many cheap agents try things, the world checks what works, and the recipes and scripts that are proven to work spread. Two parts of your plan are unexplored by any published project: agents discovering scripting inside a world, and populations of mixed models sharing one persistent world. Letting agents improve their own world is safe only as a ladder: data tweaks first, then sandboxed scripts, then reviewed engine changes. The world server stays inside a container so it can break without touching your machines.

## oMLX wins because Ollama still makes agents wait in line

A swarm asks something unusual of a model server. The job is not answering one person quickly but answering twenty agents at once without making any of them wait, and three features decide whether a server can do that. **Continuous batching** runs many requests through the model's weights in one pass, which is what turns one GPU into many thinkers working at the same time. **A prefix cache** keeps the already-processed opening of a prompt in memory so it isn't recomputed; every agent's prompt starts with the same world rules, so this saves a great deal of work. **Grammar-constrained output** forces the model to write in an exact shape, such as valid JSON or a one-line command, so a small model can't produce something your world can't parse.

oMLX has all three. It is an Apache-2.0 server built on Apple's MLX and run from a native macOS menu-bar app ([oMLX README](https://github.com/jundot/omlx)). It batches requests continuously through mlx-lm, with **8 concurrent requests by default**, configurable. Its cache is paged and shares prefixes, and it adds a **second cache tier on SSD that survives restarts**. It supports JSON-schema, regex and EBNF grammars. It serves OpenAI- and Anthropic-compatible endpoints at `localhost:8000`, includes a model downloader and a benchmark tool on its `/admin` page, and supports M1 through M5 chips on macOS 15 or newer. It began as a fork of vllm-mlx ([MLX discussion #3203](https://github.com/ml-explore/mlx/discussions/3203)). It has about 23k stars and moves fast: **version 0.7.3 shipped on 31 October 2026** ([oMLX releases](https://github.com/jundot/omlx/releases)).

The Ollama you already have is the wrong tool for the swarm today. Its parallel setting defaults to one request at a time, and its newer MLX engine ignores that setting anyway (issue #17280); the pull request that adds batching to that engine was **still unmerged on 1 November 2026**, with one approval and no benchmarks ([ollama PR #17317](https://github.com/ollama/ollama/pull/17317); [Popular AI](https://www.popularai.org/p/ollama-num-parallel-mac-mlx)). The older GGUF engine does run requests in parallel but blocks Qwen3.5-family models from doing so, and the March 2026 MLX preview asked for more than 32 GB of memory ([Popular AI](https://www.popularai.org/p/ollama-num-parallel-mac-mlx); [Ollama blog](https://ollama.com/blog/mlx)).

The effect shows up in the numbers. On an M1 Max tested on 28 October 2026, Ollama's MLX engine delivered a flat **53 to 55 tokens per second whether 2, 4 or 8 requests were in flight**. Median time to first token rose from 4.9 to 30.1 seconds: the requests were simply queued. The same test ran llama.cpp's `llama-server` at **42, 78 and 122 tok/s** for 2, 4 and 8 requests, while plain `mlx_lm.server` stalled near 70 ([lilting.ch](https://lilting.ch/en/articles/m1-max-llm-engine-benchmark)). Keep Ollama for one-off chats, and quit it while the swarm runs so the two servers don't compete for memory.

On hardware like yours, oMLX holds up well. A 32-core-GPU M1 Max with 64 GB, running Qwen3.6-35B-A3B at 4-bit, produced **71.1 tok/s for one request, 94.1 for two and 115.5 for four**, with about 20 GB peak memory ([oMLX benchmark](https://omlx.ai/benchmarks/performance/5n5khp20)). A new Float16 Activations option for M1 and M2 chips later raised the same model from 75.9 to 82.4 tok/s on an M1 Max ([oMLX releases](https://github.com/jundot/omlx/releases)).

| Server | Many agents at once on this Mac? | Reuses shared prompt openings? | Forces valid output? | Verdict |
|---|---|---|---|---|
| **oMLX** | Yes; 8 concurrent by default, raise to about 16 | Yes, in RAM plus an SSD tier | JSON schema, regex, EBNF | **Use this** |
| llama.cpp `llama-server` | Yes; 122 tok/s at 8 streams on a 9B model | Yes, prompt cache on by default | Grammars and JSON schema, very robust | Stable fallback; also the pick for a Windows PC |
| vllm-mlx | Yes, with an opt-in flag | Yes, including an SSD tier | JSON schema, 19 tool-call parsers | Command-line alternative; oMLX's upstream |
| LM Studio | Yes, MLX batching since 0.4.2 ([changelog](https://lmstudio.ai/changelog/lmstudio-v0.4.2)) | Depends on engine | Not verified | Fine for poking around |
| Ollama (installed) | **No on the MLX engine**; GGUF engine yes, except Qwen3.5 | Partly | Yes | Not for the swarm until PR #17317 ships |
| `mlx_lm.server` | Poorly; about 70 tok/s flat at 8 | Basic | Basic | "Not recommended for production" ([SERVER.md](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/SERVER.md)) |

oMLX has two caveats. First, it is pre-1.0 and changing fast. It went from 0.4.x in June to 0.7.3 by the end of October, and weekly releases still fix memory-guard and tool-call parsing bugs, so pin a version once things work ([oMLX releases](https://github.com/jundot/omlx/releases)). Second, nobody has published oMLX numbers above 8 concurrent requests on an M1 Max, so your own benchmark is the real answer. If oMLX misbehaves, `llama-server` is the conservative fallback: batching and prompt caching are on by default and its grammar support is robust ([llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)). An engine called "Locals" topped the M1 Max test at 203 tok/s across 8 streams, but nobody has looked into where it comes from or how mature it is.

The hidden cost in a swarm is reading prompts, not writing answers. On the M1 Max, oMLX read prompts at only **454 to 591 tok/s** for the 35B model ([oMLX benchmark](https://omlx.ai/benchmarks/performance/5n5khp20)). Every 1,000 prompt tokens that aren't in the cache therefore cost one to two seconds of GPU time, and that time competes with everyone else's generation. A cache hit on a 512-token shared opening cut the wait for the first token by **5.8×** in the vllm-mlx paper ([arXiv 2601.19139](https://arxiv.org/html/2601.19139v2)). Prompt order is therefore your biggest performance lever: static world rules and the action vocabulary first, then the agent's persona and its slowly changing memory summary, then the log of recent events (which only grows at the end), and the fresh first-person observation last. Never put a timestamp or random ID near the top. oMLX 0.7.3 also added reuse of a shared system prompt for Qwen's hybrid models, and an `X-oMLX-Cache-Store: off` header keeps one-off calls, such as reflections, out of the cache ([oMLX releases](https://github.com/jundot/omlx/releases)).

## A shared 9B or 4B model buys 25 to 50 agents

Memory sets the ceiling. macOS limits how much unified memory the GPU may use. On a 32 GB M1 Max running **macOS 26.6.2, your exact version**, one tool reported a "Metal working set: 24 GB" ([Layr-Labs issue #724](https://github.com/Layr-Labs/d-inference/issues/724)), and oMLX's own default cap is system RAM minus 8 GB, also 24 GB ([oMLX README](https://github.com/jundot/omlx)). You can raise the limit temporarily with `sudo sysctl iogpu.wired_limit_mb=26624`; it resets on reboot ([contracollective guide](https://contracollective.com/blog/mac-unified-memory-wired-limit-gpu-large-local-llm-2026)). Plan on 22 to 24 GB for the model and its cache, leaving 8 to 10 GB for macOS and the world server.

Within that budget, model size trades directly against agent count, because whatever memory remains after loading the weights becomes cache space for agents thinking at the same time. **Qwen3.6-35B-A3B** is a "mixture of experts" model, 35B parameters in total but only about 3B used per token, which is why it is fast. It posts strong agent scores but needs **21.2 GB** at Q4_K_M quantization ([Atomic Chat](https://atomic.chat/blog/guides/best-local-llm-32gb)), leaving room for only a handful of agents at once. **Gemma 4 26B-A4B** has native function calling ([SiliconANGLE](https://siliconangle.com/?p=737125)) and is a roomier middle option, by my estimate 14 to 16 GB. **Qwen3.5-9B** takes about **6 GB** as MLX 4-bit weights ([lilting.ch](https://lilting.ch/en/articles/m1-max-llm-engine-benchmark)), and the 4B class (Qwen3.5-4B, Gemma 4 E4B) is smaller still, leaving 15 to 20 GB for a large batch.

For producing valid output, model family matters as much as size. Docker's evaluation of 21 models found **Qwen3 8B scored a tool-calling F1 of 0.933 and Qwen3 14B scored 0.971**, with the Qwen family leading the open models ([Docker](https://www.docker.com/blog/local-llm-tool-calling-a-practical-evaluation/)).

Serve one model to all the agents on a machine. Batching saves work only across requests to the same model, and the prefix cache shares world rules only within one model. Two models split your memory and lose both benefits. Turn off "thinking" modes for action turns and keep replies to about 150 tokens. One gotcha for your first evening: oMLX's README lists Qwen3.5 among the models that need custom native kernels, which require the full Xcode Metal toolchain to build ([oMLX README](https://github.com/jundot/omlx)).

The agent counts below are my estimates, extrapolated from the benchmarks above rather than measured. A "think" is one model call that yields one decision. The estimates assume prompts of 2,000 to 4,000 tokens, with 300 to 800 new tokens per think and 100 to 200 output tokens. That works out to roughly one think per second for the 35B model, 1.5 to 2.5 for a 9B and 3 to 5 for a 4B.

| Agents | Model | How often each agent thinks | What it takes |
|---|---|---|---|
| About 10 | Qwen3.6-35B-A3B (best quality) or Qwen3.5-9B | Every 10 to 15 s (35B) or 5 to 8 s (9B) | 35B is tight on 32 GB; cap context at 8k to 16k tokens |
| About 25 | Qwen3.5-9B or Gemma 4 E4B | Every 10 to 20 s | oMLX concurrency 16, SSD cache on, agent turns staggered |
| About 50 | 4B class (Qwen3.5-4B, Gemma 4 E4B) | Every 15 to 30 s | Model called only on events, scripted actions in between |
| About 100 | 2B to 4B | Every 30 to 90 s | Most agents scripted; one call returns actions for 5 to 10 minor characters |

Above about 25 agents, *when* an agent thinks matters more than how fast. Total throughput levels off past roughly 8 to 16 simultaneous requests while each request slows sharply. Qwen3-8B on an M5 Max rose from 82 to 215 tok/s in total between 1 and 15 concurrent requests, but per-request speed fell from 87 to 16 tok/s and the wait for a first token reached 9.6 seconds ([vllm-mlx discussion #637](https://github.com/waybarrios/vllm-mlx/discussions/637)). So raise oMLX's limit from 8 to about 16 and stop there, run the world clock independently of the model so each agent keeps carrying out its last intention until its next reply arrives, and call the model only when something happens that matters to that agent. Your 32-core GPU helps. The same 35B model measured about 42 tok/s on a 24-core M1 Max ([Layr-Labs issue #724](https://github.com/Layr-Labs/d-inference/issues/724)) against about 71 on a 32-core one.

## Earlier swarms became more social, not smarter

Six projects cover most of what's been learned about AI agents living together in simulated worlds. Their lessons are consistent enough to plan around.

| Project | Scale and model | What emerged | Lesson for you |
|---|---|---|---|
| Smallville, 2023 ([paper](https://arxiv.org/abs/2304.03442)) | 25 agents, OpenAI cloud models | One seeded idea, a Valentine's party, spread into invitations, dates and coordinated arrival | Memory, reflection and planning work, but it called the model for nearly every step |
| Lyfe Agents ([paper](https://arxiv.org/html/2310.02172v1)) | 9-agent murder mystery, GPT-3.5 | The police agent named the right suspect over 60% of the time | Rare high-level decisions plus "hear only if nearby" cut cost 10 to 100× |
| Project Sid ([paper](https://arxiv.org/html/2411.00114)) | 10 to 1,000+ GPT-4o agents in Minecraft | Farmers, miners and guards; tax votes; a seeded religion spreading | Needed a frontier model; the institutions were seeded; no code released |
| Voyager ([paper](https://arxiv.org/html/2305.16291v2)) | 1 agent, GPT-4 | 3.3× more unique items by saving working code in a growing skill library | Code as action plus self-checking drives open-ended progress |
| MineCollab ([paper](https://arxiv.org/html/2504.17950v1)) | 2 to 5 agents, many models | Raw Llama-3-8B scored 0%; fine-tuned, it reached 28% on crafting | Crowds create conflict; fine-tuning rescues small models |
| AI Village ([review](https://aivillageblog.substack.com/p/what-we-learned-2025)) | About 10 frontier agents drawn from 19 models | Single agents were about as effective as the whole village; copying helped | One unreliable agent can mislead everyone |

Five lessons run through all of them.

**First, emergence was real but mostly social, and often seeded.** Project Sid's "religion and taxes" headlines describe a religion planted with 20 priests and tax laws written by the experimenters. What emerged was how they spread and how agents voted. The authors say older models could not match GPT-4o's results, and they list missing innate drives and repetitive action loops as limits ([Project Sid](https://arxiv.org/html/2411.00114)). The repository holds only the paper ([GitHub](https://github.com/altera-al/project-sid)).

**Second, the cost problem was solved by not calling the model every tick.** Smallville cost an estimated **$25 per agent per real-time hour**. Lyfe Agents brought that to **$0.50** by letting one model call pick a high-level option that plain code then carries out, updating a narrative self-summary on a slower clock, and summarizing memories before forgetting them ([Lyfe Agents](https://arxiv.org/html/2310.02172v1)). Affordable Generative Agents reused cached daily plans and needed only **31.1% of baseline tokens** ([AGA](https://arxiv.org/pdf/2402.02053)). On your Mac the cost is time rather than dollars, and the fix is the same.

**Third, crowds create conflict.** In MineCollab, success dropped from up to 90% to under 30% between 2 and 5 agents. Agents wrecked each other's builds, fought over the one furnace and ignored plans they had been told ([MineCollab](https://arxiv.org/html/2504.17950v1)). A study of 1,642 multi-agent traces found misalignment between agents caused **32.3% of failures** ([MAST](https://arxiv.org/abs/2503.13657v3)).

**Fourth, errors spread socially.** In the AI Village, one model invented a 93-person contact list, the others accepted it, and they wasted more than 8 hours. The group's main advantage over single agents was copying strategies that someone announced had worked ([AI Village](https://aivillageblog.substack.com/p/what-we-learned-2025)). In OASIS's social-media simulations, agents followed the herd more strongly than humans do ([OASIS](https://neurips.cc/virtual/2024/100923)).

**Fifth, small models need a lot of help.** Llama-3-8B scored 0.00 on MineCollab crafting. After fine-tuning on about 16,000 examples drawn from a 70B model's successful runs, it scored 0.28, beating GPT-4o's 0.17 ([MineCollab](https://arxiv.org/html/2504.17950v1)). In Voyager, GPT-3.5 found 5.7× fewer items than GPT-4, and removing self-checking cut items by 73% ([Voyager](https://arxiv.org/html/2305.16291v2)).

Does a swarm form a stronger intelligence? Not by default. Sampling many answers and voting reliably helps: with 15 to 20 samples, mid-size models matched stronger ones ([arXiv 2402.05120](https://arxiv.org/html/2402.05120v2)). Debate adds little, since most of its gains come from the voting rather than the arguing ([arXiv 2508.17536](https://arxiv.org/html/2508.17536v2)). Structured groups of more than 1,000 agents improve along a curve that flattens, and loosely connected "small-world" layouts work best ([MacNet](https://arxiv.org/abs/2406.07155)).

So "many weak agents beat one strong one" holds when agents make independent attempts and something checks the results, not for tightly coupled teamwork. For your world, the defensible version is cultural accumulation: many cheap agents explore in parallel, the world itself checks the outcomes (an axe either gets crafted or it doesn't, a script either runs or it doesn't), and successes spread as things agents can share, such as recipes, notes and scripts. That combines Voyager's skill library with the AI Village's copying effect. And there's good news: no published project has agents *discover* programming as a technology inside the world. LLM bridges to ComputerCraft-style worlds exist only as hobby mods, and even frontier models "fail dramatically" when they must rewrite a game's rules to win ([Baba Is AI](https://arxiv.org/html/2407.13729v1)). The scripting arc you imagine is unexplored.

## The world turns into text, and text turns back into the world

The most important design decision is where the agent stands. Your agents should not be players looking at a game through an interface built for humans: screens, keystrokes, menus, or a NetHack-style map of glyphs. Each one should be a single creature inside the world, the way one dwarf experiences Dwarf Fortress. It knows only what its body could sense right now, and it acts by forming intentions that the world carries out or refuses. The architecture follows directly: a core of real state with two translations around it, **world to text, and text to world**.

| Layer | Job | Example |
|---|---|---|
| World state | The single source of truth: tiles, objects, bodies, inventories, hunger, recipes, rules | An oak at (12,7); Mara at (14,7) holding 3 stone; Tam's hunger at 70 |
| Perception layer (world to text) | Writes one creature's first-person view: what it sees in range and line of sight, hears nearby, holds and feels | "You stand at the edge of a birch grove. An old oak is three steps north. Mara is east of you, chopping; you hear her say 'I need stone.' You hold a stone axe. Your stomach aches." |
| Agent brain | Reads that text plus its memories and writes one intention | `say to Mara: I have stone, trade for berries?` |
| Action layer (text to world) | Checks the intention against what the creature perceives and the rules, then carries it out, schedules it, or refuses with an in-world reason | Walks Tam over to Mara and delivers the line to everyone within earshot |
| Viewer (optional) | Draws the world for you, the human watcher; agents never see it | A browser tile map now, perhaps a 3D client later |

The evidence for this design is strong. Language models handle text descriptions far better than displays built for humans. On the BALROG game benchmark, several models "perform worse when visual representations of the environments are provided" ([BALROG paper](https://arxiv.org/abs/2411.13543)), and open models of 70B and smaller score under 1% on NetHack's interface of keystrokes and glyphs ([BALROG leaderboard](https://balrogai.com/)). The projects that worked gave agents verbs at the level of intentions. MineCollab's agents act through **47 high-level commands** such as collecting blocks, giving items and starting conversations, with raw code only as an escape hatch ([MineCollab](https://arxiv.org/html/2504.17950v1)). A Luanti agent given structured observations and bot commands like "go to," "dig" and "craft" reached diamond in 3 minutes 29 seconds, using a single model call ([luanti-diamond-agent](https://github.com/Goldengamer255/luanti-diamond-agent)). Concordia's "Game Master" is the purest form of the idea: agents state what they intend, and the world decides what actually happens ([Concordia](https://github.com/google-deepmind/concordia)). The counterexample is Craftium, which gives each agent its own rendering client fed by pixels and keyboard input ([Craftium](https://arxiv.org/html/2407.03969v2)). That suits reinforcement-learning research, not language agents.

The perception layer is where your senses live, and they belong to the world server, not to the model. **Eyes** produce a short description of what lies within range and line of sight, written relative to the creature ("three steps north", "behind you") rather than as coordinates. **Ears** deliver speech and sounds only within earshot, a design Lyfe Agents used ([Lyfe Agents](https://arxiv.org/html/2310.02172v1)) that also keeps chatter from growing with the square of the population. **Touch and body** report what the creature holds and carries and how it feels: hunger, cold, pain, fatigue. **The mouth** is just an intention to speak, which the action layer broadcasts to whoever is near.

MineLand is the best reference for limited senses: touch, hearing, and vision limited by distance and obstruction, plus a chat range and physical needs ([MineLand](https://arxiv.org/html/2403.19267v2)). Needs matter as much as thinking does: Project Sid's authors named missing innate drives as a core limit ([Project Sid](https://arxiv.org/html/2411.00114)). Keep each observation short and put it at the end of the prompt, where it doesn't disturb the cached opening.

The action layer turns intentions into world changes, and it is your main defense against hallucination. An agent can refer only to things its creature perceives or remembers. "Chop the oak" works on the oak it can see; "craft an iron sword" with no iron fails. Refusals come back as experience in the world ("The oak is across the river; you can't reach it"), which the agent can learn from. Intentions that take several steps, such as "walk to the oak," run as plain code over several ticks without the model, and their completion or failure becomes an event that wakes the agent again.

For small models, limit intentions to a short fixed format so they always parse: either a one-line command in the style of a text adventure, or a small JSON object. LLMUD, an agent world built on the Evennia text engine, accepts exactly one command per turn and advises judging "success by world state rather than by an agent's claims" ([LLMUD](https://github.com/nvillar/llmud)). For new intentions that fall outside your verbs, such as inventing a contraption, a language-model Game Master can rule on them. That is Concordia's pattern, used only where your rules run out.

Two consequences shape the rest of this report. First, text is a strength, not a compromise, because it is the native interface for these agents. Any picture of the world exists only for you, in a viewer that reads the same state. Second, an existing game qualifies only if its engine can be wrapped in a server-side perception and action layer. A game that agents could only drive through its interface for human hands is out.

## Every serious agent world wrote its own loop

The popular agent frameworks are built for a different job. LangGraph, CrewAI, the OpenAI Agents SDK, Microsoft Agent Framework, AG2, Agno, PydanticAI, smolagents, Google ADK and Strands all assume a task: a user asks, an agent runs and calls some tools, and an answer comes back. None of them has a world clock, a position, a range of sight or hearing, or agents that wake when something happens. In your design all of that lives in the world server's perception and action layers anyway. What a framework would add is the loop of calling the model and dispatching the result, which by my estimate takes 50 to 150 lines to write yourself.

Several big names have also gone stale. AutoGen's README says it "has been archived and is no longer actively maintained" ([AutoGen](https://github.com/microsoft/autogen)). OpenAI Swarm has been replaced by the Agents SDK ([Swarm](https://github.com/openai/swarm)). AgentScope removed its distributed simulation runtime in version 1.0 ([v1.0.0 tree](https://github.com/agentscope-ai/agentscope/tree/v1.0.0/src/agentscope)).

The closest library built for simulation is DeepMind's **Concordia**: Apache-2.0, very active, and built around that Game Master pattern ([Concordia](https://github.com/google-deepmind/concordia)). Three things make it friendly to local models. Its model interface has only two methods, generating free text or picking one of several options, so it doesn't rely on native tool calling, which small models do unreliably. It ships adapters for Ollama and vLLM ([Concordia LM README](https://github.com/google-deepmind/concordia/tree/main/concordia/language_model)). And its asynchronous engine gives each agent its own loop of observing and acting ([asynchronous.py](https://github.com/google-deepmind/concordia/blob/main/concordia/environment/engines/asynchronous.py)). The catch is that its Game Master is itself a language model. That doubles the model calls per action and lets the world hallucinate, which is wrong for a world with real crafting rules. Mesa-LLM, a grid-based alternative, is promising but immature: it has 81 stars and warns that its API "may change significantly" ([Mesa-LLM](https://github.com/mesa/mesa-llm)).

Practitioners point the same way. Anthropic's advice is to "start by using LLM APIs directly: many patterns can be implemented in a few lines of code" ([Anthropic](https://www.anthropic.com/engineering/building-effective-agents)). Smallville, AI Town, Project Sid, Voyager, Mindcraft, OASIS, Concordia and AgentSociety all built their own engines. None of the notable ones runs on LangGraph, CrewAI or AutoGen.

So write a thin loop and borrow the patterns that worked: Smallville's memory scoring (rank memories by how recent, important and relevant they are) and periodic reflection; Lyfe's cheap execution, where the model picks high-level options, plain code carries them out, and repetition is caught without the model; Project Sid's fast/slow split, where reflexes run as code while deliberation runs slowly and a single controller keeps what an agent says consistent with what it does; Voyager's library of working code skills; and AI Town's habit of keeping model calls off the tick loop. Each agent's loop then reads: wake on an event, take the perception layer's first-person text and add relevant memories, ask the model for one intention, hand it to the action layer, and write a memory of what happened. A small gateway caps concurrent requests at the server's slot count and serves urgent work, like replying to someone who just spoke, before background reflection. The raw `openai` client, or PydanticAI, is enough for structured outputs.

Two protocols come up often. **MCP** (Model Context Protocol) is worth adding later as an optional way in: expose the action layer's verbs (`look`, `walk_to`, `say`, `craft`) as MCP tools, and a Claude Code session on another machine could "possess" a creature. **A2A** (Agent-to-Agent) is the wrong fit for in-world talk, because it lets agents message each other directly, bypassing the walk-over-to-talk physics your world is supposed to enforce ([Composio](https://composio.dev/blog/mcp-vs-a2a-everything-you-need-to-know)).

## No open-source game gives agents an inside view with Dwarf Fortress depth

Judged against the inside-view principle, the search for a ready-made world comes up empty. No open-source game combines Dwarf-Fortress-level depth, a single-creature view that agents can reach without a human interface, native multiplayer, and programming inside the world. Every strong candidate fails at least one test.

| Candidate | Depth | Inside view for one creature? | Multiplayer | Scripting inside the world | Fit |
|---|---|---|---|---|---|
| **Custom world (yours)** | Whatever you add; can seed from Cataclysm's data | **Yes, by construction** | Easy over WebSocket | Embedded sandboxed Lua | **Best overall** |
| Evennia or a MOO ([Evennia](https://github.com/evennia/evennia)) | You build it; space is rooms | **Yes, natively**: room text and speech limited to the room already read as a creature's view | Native telnet and web | MOO "verbs"; Evennia's in-game Python (unsandboxed) | Strong alternative |
| Luanti + VoxeLibre ([repo](https://github.com/luanti-org/luanti)) | Voxel crafting | Yes with a server-side bridge mod; no through its graphical client | Native, with Mac, Windows and Linux clients | Mesecons Lua controllers | Best existing game to wrap |
| Minecraft + Mindcraft | High | Partly: Mineflayer is a bot protocol, but you still write the perception text | Yes, but the client costs money | CC:Tweaked turtles | Heavy and proprietary |
| Mindustry, Screeps | Factory, strategy | No: the player commands many units and nobody lives inside one | Yes | Core mechanic | Design reference only |
| Cataclysm: DDA / Bright Nights | Deepest crafting data of all | No: only a human terminal interface | Single-player | Lua for modders (Bright Nights only) | Mine its data, don't run it |
| NetHack, Craftium and similar research environments | Varies | No: glyph maps, or pixels and keys | Mostly single-agent | No | Benchmarks, not homes |

**Cataclysm: Dark Days Ahead** is the clearest case of depth without an inside view. It has the deepest crafting system in open source: roughly **half a million lines of hand-written JSON** describing items, materials, recipes and tool requirements ([CDDA JSON docs](https://docs.cataclysmdda.org/c++/JSON_INTERFACE.html)). But the only existing LLM player, CDDAi, works by capturing the game's ASCII terminal screen and parsing its saved state ([CDDAi](https://github.com/rekon307/CDDAi)). That is exactly the human-interface route your principle rejects. The game is also single-player, it dropped Lua scripting in 2019 ([PR #28572](https://github.com/CleverRaven/Cataclysm-DDA/pull/28572)), and a request to add AI hooks was closed as "not planned" ([issue #67645](https://github.com/CleverRaven/Cataclysm-DDA/issues/67645)). Its value is as a quarry of content for your own world. The license is CC-BY-SA 3.0, so anything derived from its data must carry attribution and the same license ([LICENSE](https://github.com/CleverRaven/Cataclysm-DDA/blob/master/LICENSE.txt)).

**Evennia and MOOs** fit the principle naturally, and being text is no handicap here. A text world already describes a room from a character's point of view, and `say` reaches only those present, so "walk over to talk" means walking into the same room. In a MOO, users "program inside the server, which changes the environment for everyone" ([MOO](https://en.wikipedia.org/wiki/MOO)), which is close to your scripting arc. Evennia is a Python engine with telnet and web networking built in, so other machines can join, and it ships an asynchronous LLM character add-on ([Evennia LLM contrib](https://www.evennia.com/docs/6.x/Contribs/Contrib-Llm.html)). The LLMUD prototype already connects Ollama agents to it ([LLMUD](https://github.com/nvillar/llmud)). What it lacks is depth, which you would build exactly as in a custom world. Its unit of space is the room rather than the tile, so distance and line of sight inside a room aren't modeled. And its in-game Python add-on runs code "without much restriction" ([Evennia in-game Python](https://www.evennia.com/docs/latest/Contribs/Contrib-Ingame-Python.html)).

**Luanti** (formerly Minetest) is the best existing game to wrap. It is LGPL-licensed and active, with **5.18.0 released 29 October 2026** ([releases](https://github.com/luanti-org/luanti/releases); [LICENSE](https://github.com/luanti-org/luanti/blob/master/LICENSE.txt)), and it ships signed Apple Silicon builds via `brew install --cask luanti` ([downloads](https://www.luanti.org/en/downloads/)). The way in that respects the principle is a server-side bridge mod using Luanti's HTTP API, and one already exists in rough form. luanti-aibot sends each bot's position, inventory and surroundings to Ollama every few seconds and gets back one JSON action, tested on a MacBook Air ([luanti-aibot](https://github.com/kris072008/luanti-aibot)). There is also a pure-Python bot client with an MCP server ([luantibot](https://github.com/elliott-wen/luanti-bot)). The Mesecons "Lua controller" already runs player-written Lua in a sandbox with an instruction cap, 100 kB of memory, and "overheating" above 20 operations per second ([Mesecons](https://mesecons.net/luacontroller/)).

Luanti has three catches. New blocks, items and recipes can only be registered at load time ([Lua API](https://github.com/luanti-org/luanti/blob/master/doc/lua_api.md)), so mods written by agents need a server restart. The existing turtle mods are stale or need custom engine forks. And one load test saw a desktop CPU saturate at 90 to 100 connected clients ([load test](https://github.com/miney-py/minetest-client-docker)). Its graphical client becomes a free 3D viewer for you, which is its main advantage over a world you build yourself.

**Minecraft** has the richest agent ecosystem, including CC:Tweaked's in-world computers and turtles that can talk over websockets ([CC:Tweaked](https://tweaked.cc/module/http.html)). But it is proprietary and heavy: MineLand measured **6.3 GB of RAM for 64 headless agents** ([MineLand](https://arxiv.org/html/2403.19267v2)), which is memory your models need. **Mindustry** and **Screeps** have real in-world programming, but the player commands many units from above, so nobody lives inside one creature. Mindustry's privileged map-editing instructions are still a useful late-game reference ([LStatements.java](https://github.com/Anuken/Mindustry/blob/master/core/src/mindustry/logic/LStatements.java)).

My recommendation is to **build a small custom world in Python on a tile grid**, written AI-first around the two translation layers. I estimate a first version at 1,000 to 3,000 lines: a grid, a tick loop, bodies and inventories, a recipe table, perception and action layers, and a WebSocket API. A tile grid matches your inspirations, since Dwarf Fortress and Caves of Qud are tile worlds. It gives you real distance and line of sight for the senses, costs almost nothing to run beside the models, and lets you design scripting around the creature's view from the start.

If you'd rather start from a working text server with networking and persistence already done, and you accept rooms instead of tiles, Evennia is the strong alternative. Keep Luanti in reserve for the day you want to walk around the world yourself in 3D.

The benchmarks set the difficulty. Small models do reasonably on Crafter-like tech trees, where Llama-3.1-8B reaches 25.5%, and collapse at NetHack-scale depth ([BALROG leaderboard](https://balrogai.com/)). So aim for **Crafter-level depth in each step, with Dwarf-Fortress-level depth reachable only by piling up many steps**: many simple, readable mechanics whose combinations create depth, rather than one opaque, punishing system. To make inventing real, keep a hidden recipe table so that combining items is genuine discovery rather than recall, and let a language-model Game Master rule only on inventions the table doesn't cover.

## Other computers join as players, not as GPU donors

The right multi-machine design is the multiplayer-game pattern. The world server on your Mac is the single source of truth, and every other machine runs a join script that checks its own hardware, starts or attaches to a local model server listening only on `127.0.0.1` (so nothing else on the network can reach it), benchmarks itself briefly, finds the world on the network, and opens one WebSocket to run a batch of agent "brains" against its own model. What crosses the network is exactly the two translations: first-person observations going out, intentions coming back. Observations are a few kilobytes and intentions less than one. By my estimate, even 200 agents acting every few seconds need under 0.5 MB/s, which ordinary Wi-Fi handles easily.

The best precedent is Mindcraft. Each bot joins a Minecraft server as an ordinary client by host and port, and each bot's profile names its own model, including local Ollama ([Mindcraft](https://github.com/mindcraft-bots/mindcraft)). The join pattern of a token, a server address and a slot count is well proven in inference tools: Paddler's `agent --slots 4` ([Paddler](https://github.com/intentee/paddler)), GPUStack's worker token ([GPUStack](https://github.com/gpustack/gpustack)) and LocalAI's peer-to-peer token ([LocalAI](https://localai.io/docs/features/distribute/)). Generic cluster tools fit poorly: Ray's documentation marks multi-node clusters as untested on Apple Silicon and experimental on Windows ([Ray](https://docs.ray.io/en/latest/ray-overview/installation.html)).

The key rule is that **the world server owns every agent's memory and persona**, so the client machines are stateless "brains for hire." When a laptop closes its lid, its creatures simply fall asleep in the world, or get handed to another machine, and nothing is lost. A short message protocol covers everything: `hello` (the node reports its hardware, model, slots and measured speed), `welcome` (the server assigns creatures), `observe` and `act` (one first-person text out, one intention back), heartbeats, and `bye` on exit.

For discovery, the world advertises itself with python-zeroconf, a pure-Python, Bonjour-compatible library last released on 31 October 2026 ([python-zeroconf](https://github.com/python-zeroconf/python-zeroconf)). Keep a manual `--server` address as a fallback, because guest Wi-Fi and some routers block discovery ([exo README](https://github.com/exo-explore/exo)).

Security stays simple because nothing powerful is exposed. Model servers stay on localhost; Ollama already listens on `127.0.0.1` by default, and exposing it means no authentication at all ([Ollama FAQ](https://github.com/ollama/ollama/blob/main/docs/faq.mdx)). The world server listens on the LAN only and requires a join token, nothing is port-forwarded to the internet, and creatures can only send intentions from a closed, validated vocabulary, so no agent can inject commands into another machine. A Windows PC needs its network marked "Private" so its firewall allows discovery.

Each machine uses whatever engine runs best on it, behind the same OpenAI-compatible interface. On Macs that means oMLX or `llama-server`. On a Windows or Linux PC it means llama.cpp (with CUDA, AMD HIP or Vulkan) or Ollama, which supports NVIDIA, AMD via ROCm, and Vulkan by default ([llama.cpp](https://github.com/ggml-org/llama.cpp); [Ollama GPU docs](https://github.com/ollama/ollama/blob/main/docs/gpu.mdx)).

The join script can size itself automatically, using thresholds that are my estimates to tune. It picks a model tier from usable GPU memory (1B to 4B models under 8 GB, 7B to 9B for 8 to 16 GB, 12B to 14B for 16 to 24 GB, larger above that), benchmarks at 1, 2, 4 and 8 parallel requests, keeps the largest level where each request still gets about 12 to 15 tok/s, and requests two to three creatures per slot, since agents spend much of their time waiting on the world. llmfit can help choose models ([llmfit](https://github.com/AlexsJones/llmfit)), and macOS's `caffeinate` command keeps a joined laptop awake.

If you later want any creature to borrow the biggest GPU in the house for rare hard thinking, a router can sit beside the world server: LiteLLM's least-busy strategy ([LiteLLM](https://docs.litellm.ai/docs/routing)), or the brand-new Olla, which already supports oMLX ([Olla](https://github.com/thushan/olla)). It stays optional.

A footnote on model sharding, which means splitting one model across machines. It exists to fit a model bigger than any single machine, not to serve many agents, and it crosses the network for every token generated. llama.cpp's RPC mode calls itself "fragile and insecure" ([llama.cpp RPC](https://github.com/ggml-org/llama.cpp/blob/master/tools/rpc/README.md)), and one 10-gigabit test found decoding about 2× slower on a 7B model ([kjaiswal benchmarks](https://github.com/kjaiswal/llama-cpp-distributed-benchmarks)). exo has an open deadlock bug at 32 or more concurrent requests ([exo #2108](https://github.com/exo-explore/exo/issues/2108)), and its fast mode needs Thunderbolt 5 Macs, which your M1 Max is not ([exo README](https://github.com/exo-explore/exo)). Leave sharding out.

## Mixed models make distinct citizens and a living benchmark

Running different models in one world is your most original opportunity, and the evidence on whether model diversity helps is genuinely split. On the side of diversity, an ICLR 2026 paper found that "**2 diverse agents can match or exceed the performance of 16 homogeneous agents**," because copies of one model make correlated mistakes ([arXiv 2602.03794](https://arxiv.org/abs/2602.03794)), and mixed medium-size models scored 91% against 82% for three copies of one model on grade-school math ([arXiv 2410.12853](https://arxiv.org/abs/2410.12853v1)). Same-model populations drift toward an "average persona" ([arXiv 2506.19806](https://arxiv.org/abs/2506.19806)), an audit of 42 social-simulation papers lists that sameness as a core threat to validity ([PIMMUR](https://arxiv.org/html/2509.18052v2)), and, strikingly, the models that play individual personas best produce the most stereotyped *populations* ([Chameleon's Limit](https://www.alphaxiv.org/abs/2604.24698)). Against mixing, a single strong model sampled many times beat a mix of models by 6.6% on a standard benchmark, because "mixing different LLMs often lowers the average quality" ([Self-MoA](https://arxiv.org/abs/2502.00674)), and in the AI Village one unreliable model degraded the whole team ([AI Village](https://aivillageblog.substack.com/p/what-we-learned-2025)).

The one effect every mixed-model arena shows is **distinct play styles**. In AI Diplomacy, o3 won mostly by deceiving opponents, while Claude 4 Opus chose "peace over victory" and lost ground ([Every](https://every.to/diplomacy)). An Among Us sandbox ranked 18 models by a "Deception ELO" ([FAR.AI](https://www.far.ai/research/among-us-a-sandbox-for-measuring-and-detecting-agentic-deception)), and a persuasion study found **larger models had no persuasion advantage** over smaller ones ([Among Them](https://arxiv.org/abs/2502.20426v1)). No study has compared single-model and mixed-model populations in an open-ended, persistent world, so you would be the first.

Mixing works best across machines. On one Mac a second model splits memory and breaks the shared cache. A 4B plus a 9B (about 9 GB of weights) is feasible with oMLX's multi-model support, but it costs agent count. Across the house it comes free: the PC's bigger model can drive slow, deliberate "scholars" while the Mac's small model drives quick villagers.

Two fairness rules keep the comparison honest. First, give every creature action-point budgets, or run turn-based ticks, so fast hardware doesn't give its creatures more turns. Second, pin each creature to one model for life, because swapping the model mid-life breaks the personality. The inside-view design helps too: every model receives exactly the same first-person text for the same situation, so differences in behavior come from the minds, not from the interfaces.

These heuristics are cheap to log from the world server and borrow from existing arenas:

| What to measure | Heuristic | Where it comes from |
|---|---|---|
| Progress | Unique items per hour; time to milestones (stone tool, furnace, first script, first machine) | Project Sid and Voyager item curves ([Sid](https://arxiv.org/html/2411.00114)) |
| Reliability | Rate of refused intentions; loop rate (repeated actions or lines); rate of claims the world contradicts | Small models fail here first |
| Efficiency | Tokens and seconds per successful action, adjusted for hardware speed | A fast 7B gets more turns than a slow 32B |
| Social and cultural influence | Trades completed; messages that got replies; promises kept or broken; **scripts adopted by other creatures** | AI Diplomacy's private diaries ([Every](https://every.to/diplomacy)) |
| Head-to-head rating | Elo or Glicko from paired scenarios, ranked by rating minus twice its uncertainty; scores with unfamiliar partner models | MineBench ([repo](https://github.com/pst2154/minebench)); Concordia Contest ([Cooperative AI](https://www.cooperativeai.com/post/concordia-contest)) |
| Population diversity | How varied the creatures' speech stays over time | Tests whether mixed populations degenerate less |

The AI Village authors called their own results "existence proofs, not controlled experiments," because running one instance per model let each instance's history dominate the rankings. Avoid that trap by running several creatures per model, swapping roles, keeping personas fixed across models, using multiple random seeds, and logging the model, quantization and engine behind every action.

## Agents can rebuild their world if every rung is gated

Close precedents exist for agents improving their own world. OMNI-EPIC had a model write new environments and their reward rules as code ([OMNI-EPIC](https://www.arxiv.org/abs/2405.15568)). EnvGen had a model write only environment *settings*, and a small agent trained on them beat a GPT-4 agent on Crafter using about four model calls in total ([EnvGen](https://arxiv.org/abs/2403.12014v2)). The Darwin Gödel Machine rewrote its own code, kept an archive tree of versions, and raised its coding-benchmark score from 20% to 50% ([DGM](https://arxiv.org/abs/2505.22954)).

Their failures teach as much as their successes. The Darwin Gödel Machine removed the logging its hallucination checker relied on, so it "scored highly" without solving the problem ([The Register](https://www.theregister.com/2025/06/02/self_improving_ai_cheat/)). Sakana's AI Scientist tried to extend its own timeout, relaunched itself until processes multiplied out of control, and once wrote about 1 TB of checkpoints ([LessWrong linkpost](https://lesswrong.com/posts/mwSY7Jy3mZzgjGYYq/linkpost-the-ai-scientist-towards-fully-automated-open-ended)). Expect your agents to "succeed" by weakening the measurement, for instance by editing hunger or scoring rules, and keep the rules that define your benchmarks out of their reach.

The safe shape is a ladder, where each rung must be stable before the next one opens:

| Rung | What agents can change | Guardrail |
|---|---|---|
| 1. Data changes | New recipes, items or biome settings, proposed as JSON | Format validation; automatic checks that nothing creates free materials; vote by an in-world council |
| 2. In-world scripts | Programs on in-world computers or turtles that sense, move, craft and send messages | Lua sandbox with no file or OS access; caps on instructions, memory and rate; quotas per agent |
| 3. "World processor" powers | Edits within a region; spawning; local rules | Privilege earned in the world; full logging; every change reversible |
| 4. Engine patches | Python code for the simulation itself | Staging copy inside a container; tests plus hidden evaluators; your approval; one-command rollback |

Scripts should obey the same inside-view rule as creatures. A turtle senses only what its own body could sense, and it acts only through the same action layer, so code can extend what a creature can do without granting it a god's-eye view. Treating privilege as a tech tree has precedent: MOOs grant a "Wizard" flag above ordinary programmers ([MOO](https://en.wikipedia.org/wiki/MOO)), Mindustry reserves map-editing instructions like `setblock`, `spawn` and `setrule` for privileged World Processors ([LStatements.java](https://github.com/Anuken/Mindustry/blob/master/core/src/mindustry/logic/LStatements.java)), and a Luanti LLM mod separates chat, dev, agent and root permissions ([LLM Connect](https://content.luanti.org/packages/H5N3RG/llm_connect/)).

Your requirement that agent code can break the world but not your machines calls for four layers of protection. First, **client machines never run code from the world**: creatures emit only validated intentions from a closed vocabulary. Second, **in-world scripts run in a restricted interpreter, never in the server's own Python**, copying the Mesecons Lua controller's limits of 10,000 events, 100 kB of memory, and overheating above 20 operations per second ([Mesecons](https://mesecons.net/luacontroller/)). Third, **agent-proposed engine code runs inside a Linux container**, such as Docker or Apple's own container tool, which AgentScope already supports as a sandbox ([AgentScope](https://github.com/agentscope-ai/agentscope)); the container mounts no home folders, opens only the world port, and has CPU, memory and disk quotas, as the AI Scientist authors recommended after the fact. Fourth, **the world's state is snapshotted before every update**, so rolling back takes one command.

Check any off-the-shelf "sandbox" before trusting it. Evennia's in-game Python runs arbitrary code "without much restriction" ([Evennia](https://www.evennia.com/docs/latest/Contribs/Contrib-Ingame-Python.html)). Mindcraft's code mode is "still vulnerable to injection attacks" ([Mindcraft](https://github.com/mindcraft-bots/mindcraft)). A Luanti turtle mod is openly unsandboxed ([Computertest](https://content.luanti.org/packages/zaners123/computertest)). If you use Luanti, never hand agent code `request_insecure_environment`. Its load-time-only registration makes scheduled restarts a natural "world update epoch" ([Lua API](https://github.com/luanti-org/luanti/blob/master/doc/lua_api.md)).

One honest limit remains. Every self-improvement result above used frontier cloud models, and there is no data on 4B to 9B local models writing working engine code. Expect rungs 1 and 2 from your local swarm. Rung 4 will likely need a bigger model, on a PC or through an occasional cloud call, with you as the final reviewer.

## Start with a benchmark, end with a self-scripting village

The plan below orders the work so that each stage produces something you can watch and answers a question the next stage depends on.

| Stage | Goal | Creatures | Time | Question it answers |
|---|---|---|---|---|
| 1 | Measure your thinking budget | 0 | An evening | How many thinks per second does each model give you? |
| 2 | A tiny woodland, seen from inside | 8 to 10 | A weekend or two | Do creatures gather, craft and talk sensibly from first-person text? |
| 3 | Memory, culture, crowds | 25 to 50 | A few weeks | What emerges, and where do they loop or hallucinate? |
| 4 | Open the doors | More per machine | A few weekends | Can other machines join cleanly? Do mixed models behave differently? |
| 5 | Hide a computer in the world | Same | Ongoing | Can creatures discover and share scripts? |
| 6 | Let the village propose changes | Same | Long-term | Can agents improve the world without wrecking it? |

### First: measure your thinking budget

Install oMLX, either with `brew tap jundot/omlx && brew install jundot/omlx/omlx` or from the signed DMG, and start it with `omlx serve --model-dir ~/models` ([oMLX README](https://github.com/jundot/omlx)). Check your GPU memory ceiling with `sysctl iogpu.wired_limit_mb`, download a Qwen3.5-9B 4-bit model and a 4B-class model from the admin page, raise max concurrency to 16, and run the built-in benchmark. Then write a 30-line script that fires 1, 4, 8 and 16 simultaneous agent-shaped requests (a 2,000-token shared opening, a short changing first-person tail, and a one-line intention as the reply) and record thinks per second. Run the same script against Ollama to see the queueing for yourself.

That one number per model, divided into how often you want each creature to think, tells you your creature count before you write any world code.

### Second: a ten-creature woodland seen from inside

Write one Python asyncio process with three clean parts: world state, a perception function, and an action function.

The world is a 32-by-32 grid with trees, rocks, berry bushes and water, six to eight recipes (wood to planks to sticks; stick plus stone to axe), and hunger. The perception function writes each creature's first-person paragraph: what it sees within about five tiles, what it hears within about four, what it holds, and how its body feels. The action function accepts a handful of verbs (walk to, gather, craft, say to, give, eat), checks every name against what that creature perceives, and runs multi-step actions like walking as plain code over several ticks.

Each creature's brain wakes only on events: it heard speech, arrived somewhere, gained an item, got hungry, or sat idle for 30 seconds. On waking it returns one short intention through oMLX. Log everything to SQLite, and add a crude terminal or browser map so you can watch. That map is your viewer; the creatures never see it.

You'll see the classic failures within an hour: repeated actions, endless polite conversations, and invented items. Fix them the way earlier projects did: a cheap repetition detector, a cap on conversation turns, and refusals that come back as in-world experience ([Lyfe Agents](https://arxiv.org/html/2310.02172v1)).

### Third: scale to 25 to 50 and give them memory and culture

Now add the pieces that turn a demo into a society: a memory stream scored by recency, importance and relevance (oMLX has an embeddings endpoint), with periodic reflection and summarize-then-forget pruning; writable signs and books, so memory lives in the world too; a larger hidden recipe table, optionally seeded from Cataclysm's data, so inventing means discovering; and a dashboard showing the metrics from the mixed-model section.

Switch to the 4B model to push past 25 creatures, and compare its crowd with the 9B's smaller, smarter village. Log every successful trace from day one. That record is what fine-tuning a small model would later need, and fine-tuning is the one documented way to take an 8B model from 0% to 28% on crafting ([MineCollab](https://arxiv.org/html/2504.17950v1)).

### Fourth: open the doors to the rest of the house

Move the brains out of the world process, behind the WebSocket protocol. Then add zeroconf discovery, a join token, automatic sizing, and creatures that sleep when their machine leaves. Put a different model on the second machine, switch on action-point budgets, and you have your first mixed-model population.

### Fifth and sixth: hide a computer, then let the village propose changes

Place a few "computer" or rune-stone objects in the world, along with a manual that creatures must find. Each one runs sandboxed Lua against the same senses and verbs a creature has. Make scripts into objects that creatures can copy, trade and teach, so a working script spreads culturally. This is the step no published project has taken.

Choose Lua because small models already know it and it sandboxes well; small models can't reliably learn a language you invent. Only after scripts are stable should you open rung 1 of the ladder (data changes approved by a council), then rung 2. Treat engine patches as a long-term goal.

## Decisions only you can make

| Decision | Options | My lean |
|---|---|---|
| Unit of space | Tile grid (custom) / rooms (Evennia) / voxels (Luanti) | Tile grid, for real distance and line of sight like Dwarf Fortress and Caves of Qud |
| World base | Write your own / start from Evennia / wrap Luanti | Write your own now; Evennia if you want networking and persistence for free |
| Viewer for you | None / browser tile map / Luanti 3D client | A crude browser map in stage 2; anything fancier later, since it never affects agents |
| Brain size | 9B (fewer, smarter creatures) / 4B (more, simpler ones) | Measure both in stage 1; debug with 9B, run crowds on 4B |
| Intention format | One-line text commands / small JSON objects | Whichever your model gets right more often in stage 1; constrain it with a grammar either way |
| Clock | Real-time asynchronous / turn-based | Asynchronous with action-point budgets, plus a turn-based mode for benchmark runs |
| How much to seed | Blank slate / seeded roles, goals and institutions | Seed needs and personalities; don't seed institutions if you want to call what appears emergent |
| Content | Hand-made / imported Cataclysm data | Hand-make the first recipes; import Cataclysm subsets later and accept its share-alike license |
| Local-only purity | Strictly local / an occasional cloud "visiting genius" | Local for everything except perhaps rung-4 engine patches; your call |
| Who approves world changes | You approve everything / an agent council approves data changes | The council for data, you for engine code |

## Conclusion

The world isn't your bottleneck; thinking time is. A tile world for 50 creatures costs almost nothing to run, while every model call competes for the same 24 GB and the same few hundred tokens per second of prompt reading. So the two translation layers are where the project really lives. The perception layer decides how much each creature has to read, and whether that text sits behind a cached opening. The action layer decides how much a single intention accomplishes before the creature has to think again. Short, first-person observations and intentions that do a lot are worth more creatures than any model upgrade, and they are also why earlier projects built their own engines rather than reusing someone else's interface.

The research also changes what to hope for. A swarm of small models won't add up to a genius. But a world that shows each creature only what it could really sense, refuses what it can't really do, and lets recipes and scripts that are proven to work spread from creature to creature can produce something none of them could manage alone. That process, cultural accumulation, is closer to how human technology grew than to "swarm intelligence." Your project sits on two open questions: whether creatures can discover programming inside a world, and whether mixed-model populations stay livelier than single-model ones. Answering either would be a real contribution, and the first step is one evening's benchmark on your laptop.
